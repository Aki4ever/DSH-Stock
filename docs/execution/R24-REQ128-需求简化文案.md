# R24 · REQ-128 需求简化文案与实施记录（网页服务「开机自启常驻响应」）

> **登记为 `REQ-128`** · 实施版本 `v5.17.0`（**基础设施补丁**：无前端/接口载体变更，故不进版本号）
> 任务命名：`[新需128][85] 网页开机自启修复`
> 用户原话：「1、如图1,重启电脑后,打开网页提示这个,修复这个问题,需要在每次打开网页都有响应;如果不行的话,就做一个单独启动的本地页面;」
> 用户诉求图：浏览器 `ERR_CONNECTION_REFUSED`（`127.0.0.1 拒绝了我们的连接请求`）

---

## 一、简化后的可执行需求文案（实施前冻结）

**目标**：重启电脑后**无需任何手工操作**，打开 `http://127.0.0.1:8888` 必定有响应。
**方案 A（主选）**：注册用户级 LaunchAgent（登录即拉起 + 定期兜底复查），**唯一启动口径**复用 `scripts/ensure_server.sh`（幂等）。
**方案 B（兜底）**：若 A 受平台限制不可行，做一个「可单独启动的本地入口」，双击即拉起服务并打开页面，且**绝不留下白屏无解释**。

**验收标准（全部实跑，逐条留痕）**
1. 冷启动：全量停掉（模拟关机）后，由 launchd 装载 plist，服务端**自动**就绪；
2. `launchctl print gui/$UID/com.dsh.stock.web` 为已装载且退出码正常；
3. 幂等：连续 3 次 `ensure_server.sh`，8888 上**始终只有 1 个**监听进程；
4. 自愈：`kill -9` 服务端后秒级自动复活；
5. 半死态：看门狗单独死亡时被补位，且**不重启**在途服务端；
6. 无静默失败：任何失败都有中文原因 + 日志路径。

**红线**：不改 8888 端口语义与 `/api/*` 契约；`start_server.sh` / `stop_server.sh` 的 PID/端口口径**只做加法不改动**；仅绑 `127.0.0.1`（沿用 REQ-049）。

## 二、实测根因（三条，全部有磁盘/日志证据）

**① 缺的是「出生」，不是「保活」**
工程原本已有两道保活：`scripts/ensure_server.sh`（幂等拉起）+ `scripts/watchdog.py`（进程级自愈，
watchdog.log 实测留有 19 次 `自动自愈重启` 记录）。但两者都只在「进程被别人 kill」这类场景有效：
重启电脑后进程与看门狗一起消失，`~/Library/LaunchAgents` 里**没有任何本项目条目**——
`watchdog.log` 末行 `[2026-10-08 08:17:32] 收到停止信号，退出看门狗守护` 就是关机时被一起收走的留痕。
⇒ 用户打开网页必然 `ERR_CONNECTION_REFUSED`。

**② macOS TCC 保护 `~/Documents`（本批最硬的物理约束）**
直接注册「launchd → `/bin/bash` 执行工程脚本」后实测失败，`launchd.log` 留痕：
```
shell-init: error retrieving current directory: getcwd: cannot access parent directories: Operation not permitted
/bin/bash: /Users/linqiyu/Documents/DSH/DSH股票/scripts/ensure_server.sh: Operation not permitted
last exit code = 126
```
对照探针（脚本挪到 `~/Library/Application Support`、工作目录 `/tmp`）同样 `READ_DOCUMENTS=fail`：
**拦截点是「读文稿目录」这件事本身，与脚本放哪无关** —— 纯 launchd 路线不授予「完全磁盘访问权限」不可能成功。
反证（同机实测）：以 `ELECTRON_RUN_AS_NODE=1` 运行 DSH 应用本体
（`/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness`，签名身份 `com.deepseek.dsh`，
已具备文稿访问授权）时 `READ_DOCUMENTS=ok`。

**③ `.server.pid` 竞态（连带发现并修复的真实缺陷）**
`server.log` 实证：健康实例写下 `🟢 进程 PID: 13464 (已写入 .server.pid)` 之后紧跟
`❌ 启动失败: 端口 8888 可能已被占用 ([Errno 48] Address already in use)`，随后 `.server.pid` **消失**
而 13464 仍在监听。根因是旧实现「先写 PID 再 bind」+「失败路径无条件 `os.remove(PID_FILE)`」：
抢端口失败的重复实例把**健康实例**的 PID 文件删了，`stop_server.sh` / watchdog 因此失去权威句柄。

**④ 看门狗冷启动抖动死循环（终局验收实测抓到，顺手修掉）**
`watchdog.log` 实证：`✅ 服务端已成功重新拉起 (新 PID: 19450)` → 下一秒起连续两次探针失败 →
再次重启（`新 PID: 19473`），每个实例活不到 7 秒，服务**永远起不来**。
根因：`restart_server()` 拉起后只 `sleep(1.5)` 就交回主循环，而主循环「2 秒一探、连续失败 2 次即重启」，
本机服务端要全量加载 SQLite 底册（4,601 只）后才 bind，实测冷启动需 **5~10 秒** ——
于是看门狗**反复 SIGKILL 自己刚刚拉起的实例**。这条与「打开网页就有响应」直接冲突，属本批必修。

## 五、如实登记的边界（不美化）

1. **electron 模式依赖 DSH 应用存在**：家长进程是 `/Applications/DeepSeek Harness.app/...`。
   若该应用被删除/改名，LaunchAgent 会启动失败——此时改用 `install_autostart.sh install --legacy-bash`
   并**一次性**给 `/bin/bash` 授予「完全磁盘访问权限」（系统设置 → 隐私与安全性 → 完全磁盘访问权限），
   否则 TCC 必然给出退出码 126（脚本 `status` 会显式告警，不静默）。
2. **本批**未**升级产品版本号**：改动全部落在运维脚本层，前端徽标与静态缓存串仍为 `v5.17.0-r23`，
   与 `config/version.json` 严格同源（避免为了补丁去改前端载体反而制造缓存假绿）。
3. **StartInterval=300 是刻意的**：秒级自愈由 watchdog（2 秒探针）负责，launchd 只负责「登录出生」与
   「两道防线都死」的兜底，避免每分钟拉起一次 Electron 进程的无谓开销。
4. **方案B 首次双击可能弹一次系统授权**（「终端 想要访问"文稿"文件夹」→ 允许），这是 macOS TCC 行为，
   非实现取舍；授权后长期有效。
5. **本批未做**：把工程迁出 `~/Documents`（会连带影响爬虫、数据库与既有运维口径，收益不足以抵消风险）；
   为 `stop_server.sh` 增加「无 PID 文件时的兜底提示」（当前靠 `lsof` 兜底已可停服务）。
6. **看门狗宽限期 30 秒是刻意取值**：它必须大于本机冷启动（实测 5~10 秒）且留足余量；
   代价是「服务端真的卡死」时最多晚 30 秒才进入下一轮判定 —— 用可靠性换恢复时延，方向明确（宁晚不晃）。
